# Thật Space execution plan: complete community and Bà Mối

Prepared 2026-10-01 after the user asked about the rest of Thật Space, then
corrected to the user's explicit phase boundary: complete the community and
Bà Mối. Full Tử Vi charts, generated readings, reading history and PDFs are
out of scope for this phase. Future astrology work should reuse Moon; this
phase does not rebuild Moon. The plan is not implementation/deployment evidence.

## Current baseline and product boundary

- The Next.js forum, member profile, Tử Vi form, reading history, and
  matchmaking directory are demonstrations with fixed data. They are not
  production member flows. The reading/PDF buttons and reply form do nothing.
- The Bà Mối service is implemented and locally verified: 31 test files,
  302 tests, typecheck, lint, and production build passed. Its live Discourse
  integration remains unverified. See [local readiness](../local-beta-readiness.md).
- The current [v3 architecture](../ba-moi-spec.md) makes Discourse the member
  experience and authentication authority. Keep the Next.js pages as a public
  demonstration/marketing reference; build the actual community in Discourse.
- Full Tử Vi charts, generated readings, private reading history, and PDFs
  remain out of scope, as already stated in v3 and reaffirmed by the user.
  Existing tuổi/day-pillar compatibility calculations stay in Bà Mối; no
  full-chart engine or romantic-score port is added in this phase. The Tâm
  linh & Tử Vi forum category can support member discussion without a chart
  generation feature.

No paid always-on server is necessary to begin development. A running
Discourse instance is necessary to prove real community and bot behavior;
it can be a local development instance first. Production hosting is a later
step. ASUS was still serving Atum/Taylor on the last read-only check, and AWS
has not been provisioned for this app.

## Phase 1: prepare the community and prove its smallest working path

Create versioned community manifests under `discourse/community/`: categories,
groups and permissions, site settings, onboarding fields, and automation
mappings. Pin Discourse/plugin/theme-component revisions and record their
licenses. Commit only placeholders for hostnames and credentials.

Use the official [macOS development guide](https://github.com/discourse/discourse/blob/main/docs/developer-guides/docs/02-development-environments/04-macos-setup.md)
to establish a local instance before choosing paid production hosting. On
2026-10-01, Docker and Colima binaries were installed, the default Docker socket
was absent, and `colima status` reported not running. No instance was started
by this planning task. Do not assume the older x86-only development image will
boot on Apple Silicon; the [Docker development guide](https://github.com/discourse/discourse/blob/main/docs/developer-guides/docs/02-development-environments/03-docker-setup.md)
documents that limitation. Verify the selected runtime against the pinned
source before installing dependencies.

First acceptance slice, with two members and one administrator:

1. An invitee signs up, completes configured fields, and is activated by staff.
2. The member logs in, creates a topic, replies, edits her own content, and
   receives an in-app notification.
3. A second member can read/reply within permitted categories; a guest and
   unapproved account cannot read protected content or uploads.
4. A member flags content; a moderator reviews it and takes an allowed action.
   Selecting Artist or Host never grants staff privileges.
5. These paths work on a narrow mobile screen and survive a service restart.

Keep first-slice access restrictions and credential handling in place from
the start. Add optional components only after this path succeeds.

## Phase 2: complete the community experience

After Phase 1 passes, add and verify these vertical slices in order:

1. Profiles: editable bio/header, permitted answers, activity, badges and a
   featured topic. Verify another member sees only the intended information.
2. Artwork: Triển lãm image posts, image tiles and the Tác phẩm profile tab.
   Check author ownership, upload access and mobile rendering.
3. Retreats/workshops: an event, its detail view, RSVP and member notification.
   Confirm Host permissions permit intended actions without staff access.
4. Following: user/topic/category following where supported by the pinned
   platform and component set; verify the resulting notification behavior.
5. Theme: Vietnamese labels, existing branding, clear forum/profile/events/
   artwork/Bà Mối navigation, keyboard access and phone layouts.
6. Operations: Thảo's moderation/admin guide, flag handling, account recovery,
   onboarding changes and content administration. Configure and verify the
   v3-required Discourse AI spam/toxicity detection after ordinary moderation
   is proven and the model/configuration is available.

Member navigation must reflect this phase: forum, profiles, artwork, events
and Bà Mối. Do not offer inactive reading/chart/PDF buttons as working member
features. The public Next.js mockup may remain clearly labelled as a demo.

Deliver source-controlled configuration/theme plus an acceptance record, not
only screenshots or changes left in an admin panel. Verify plugin compatibility
and pin the exact successful revisions before declaring a slice complete.

## Phase 3: integrate Bà Mối with real accounts

Depends on a stable Discourse identity, private-message permissions and a
reachable service. The backend already exists; do not rebuild its demo UI.

Install the agent/tools, create the relay bot, bind separate single-user bot
keys, configure the signed `post_created` webhook and retry schedule, and run
the installer drift check and probe. Use the existing
[live acceptance checklist](../local-beta-readiness.md).

Two real members must complete consent → interview → card preview/confirmation
→ discovery → interest/response → anonymous relay → mutual reveal → end/block.
Also exercise wrong credentials, bad webhook signatures, unauthorized topic
participants, daily limits, held contact details, outage/retry and stale
consent behavior. Record phone/model observations separately from local test
evidence. Consent must disclose staff visibility into beta PMs and retained
Discourse history after service-data deletion.

## Phase 4: provision, verify and launch

Choose AWS or a confirmed-free ASUS only when a persistent, reachable instance
is needed. Translate the host-specific [setup runbook](../discourse-setup.md)
to the chosen hostname/network; do not blindly execute the historical ASUS
commands. Prepare the service deployment using the existing local-prebuilt
Vercel policy, preserve project/environment boundaries, and keep Git auto-deploy
off. Normal CI uses GitHub-hosted runners.

Before inviting beta members, prove backup/restore, restart recovery, queue
recovery, credential rotation, moderator visibility, protected upload access,
and the complete mobile member flows on the actual deployed revision. Record
the no-email recovery procedure, contact-filter limits, delivery crash window
and deletion semantics. Take a database backup before any live data migration.
No production promotion follows merely from passing local tests.

This phase is complete after the community features and Bà Mối in Phases 1–3
pass the production checks above. Full Tử Vi/chart/reading/PDF functionality
is not a completion gate. Historical Circle renewal is 2026-10-27; track
cancellation separately, without sending messages or changing subscriptions
as part of this plan.

## Parallel MECE workstreams

The coordinator owns shared architecture decisions, assembly, verification,
review and Git/PR operations. Bounded workers own disjoint outputs:

| Workstream | Ownership | Can begin |
| --- | --- | --- |
| Community configuration | `discourse/community/`: categories, groups, settings, 15 fields, permission and automation mappings | Now; runtime application waits for Phase 1 instance |
| Member presentation | `discourse/theme/`: branding and member navigation; pinned portfolio/gallery component configuration | Now for theme foundation; field rendering waits for stable field IDs and permissions |
| Service integration | Existing Bà Mối installer/probe and service configuration; bot/webhook/cron acceptance | Local checks now; real-account integration waits for Phase 1 and reachable service |
| Acceptance/operations | `docs/acceptance/` and community/Bà Mối fixtures: member journeys, moderation, recovery and deployment evidence | Test cases/runbooks now; execution follows the relevant working slice |

Dependency edges are intentional: field IDs/permissions → field automation and
theme rendering; core account/topic flow → community extensions; Discourse
identity/private PMs + service URL → live Bà Mối; assembled community/Bà Mối
features + restore proof → member invitations. Workers do not
parallelize those dependent steps or run separate reviews, CI or PRs.

Use one plan-execute-assemble cycle per coherent outcome: implement independent
scopes, integrate and run focused checks, then one assembly review through
agent-jobs for substantive code. Supporting plans/notes stay with that outcome.
